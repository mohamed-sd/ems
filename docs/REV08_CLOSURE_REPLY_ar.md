## §1 — البند 1: برهان التصحيح وبصمة الناشر (G3 · ADR-16)

### تركيبة البصمة من الكود الحيّ (لا من الوثائق)

`includes/timesheet_event_hook.php:83`:

```php
$idem = ServerId::idempotencyKey('equipment.hour_logged', 'timesheet', $tsId) . ':a' . $gen;
```

حيث `$gen = intval($level4RowId)` — **معرّف صفّ اعتماد المستوى 4**. الناتج الفعلي:

```
equipment.hour_logged:timesheet:{timesheet_id}:a{level4_approval_row_id}
```

أي أن البصمة = نوع الحدث + معرّف السجل المصدر + **نسخة الاعتماد** — مطابقة لتركيبة ADR-16 الثلاثية. مصدرُ النسخة هو «الخيار 2» المعياري من الطلب مُحسَّنًا: بدل `COUNT(*)` القابل للسباق، يُستخدم **معرّف صفّ الاعتماد النهائي نفسه** (كل نقضٍ وإعادةِ اعتمادٍ يُنشئ صفَّ مستوى-4 جديدًا = جيلًا جديدًا رتيبَ التزايد لا يُعاد استخدامه أبدًا). فتصحيحُ سجلٍّ معتمد = بصمةٌ جديدة = **حدثٌ مستقلٌّ لا يُبتلَع**، وإعادةُ إرسال الجيل نفسه تبقى معطَّلةً بالعطالة.

> **مخاوف الطلب كانت في محلّها منهجيًّا** — والفحص أثبت أن الآليّة **قائمةٌ في الكود أصلًا** منذ K5 (وليست إصلاحًا جديدًا)؛ المُنجَز الجديد هو **البرهان المؤرشف القابل لإعادة التشغيل** أدناه.

### مخرَج `tests/proof_correction.php` حرفيًّا (تشغيل 2026-07-14 — عبر الخطّاف والناشر والموزّع الحيّين)

```
بذر ساعةٍ تجريبيّة: timesheet #260 (شركة 4، executed=8)

الأحداث المنشورة لهذه الساعة: 2 (المتوقع 2)
  - equipment.hour_logged:timesheet:260:a1  quantity=8.0000
  - equipment.hour_logged:timesheet:260:a2  quantity=6.0000

التسليم عبر EventDispatcher (مستهلك رمّي zz_proof_probe من المؤشّر 55):
  تسليم → equipment.hour_logged:timesheet:260:a1  quantity=8.0000
  تسليم → equipment.hour_logged:timesheet:260:a2  quantity=6.0000
  [dispatcher] zz_proof_probe: processed=2 failed=0 dead_lettered=0 cursor=58

  الجيلان مستقلّان (a1 + a2)          ✓
  إعادةُ إرسال الجيل 1 أُهمِلت (n=2 لا 3) ✓
  التصحيح حمل القيمة الجديدة (8 و6)     ✓
  الموزّع سلّم الجيلين لمستهلكٍ مشترِك    ✓

PASS: حدثان مستقلّان، والتكرار مُهمَل، والتصحيح لم يُبتلَع وحمل قيمته الجديدة، وسُلِّما معًا
تنظيف: الدفتر عاد إلى 10 (المتوقع 10) ✓
```

**سطرا التسليم** هما سطرا `تسليم → …a1 / …a2` أعلاه: مستهلكٌ مشترِك عبر `EventDispatcher` الحقيقي (لا محاكاة) استلم **الجيلين معًا** — الأصل (8 ساعات) والتصحيح (6 ساعات). السيناريو المخوف في الطلب («التصحيح يُبتلَع مكرَّرًا وتبقى الأرقام القديمة») **منفيٌّ ببرهانٍ حيّ**. البرهان ذاتيُّ التنظيف: مستهلك المالية الحيّ لم يُمَسّ (مؤشّره 141 قبل وبعد)، والدفتر عاد إلى 10.

**معيار القبول** (تصحيح السجل نفسه = حدثٌ جديد، REV-04 §8): ✓ مستوفى.

## §3 — البند 3: قلب المحلّل Fail-Closed (G10 · ADR-24)

### التنفيذ — مع قياسٍ فرض تكييف خطة التفعيل

الصمّام `ems_failclosed_screen_guard` (في `includes/permissions_helper.php`، يستدعيه مُنفِّذ عرض الصفحة عند `id === null` حصرًا) بقائمتين من `.env`:

- `EMS_FAILCLOSED_ENFORCE_PREFIXES` → **403** بجسم JSON + سطر `UNREGISTERED_SCREEN_DENY`.
- `EMS_FAILCLOSED_MONITOR_PREFIXES` → سطر `UNREGISTERED_SCREEN_WOULD_DENY` **بلا حجب** (شفافية مُجرَّدة).
- `EMS_LEGACY_TRANSPARENCY_DEADLINE=2026-09-30` — مهلة الشفافية القديمة، تُطبع في كل سطر رصد.

**القياس الذي كيّف الخطة** (مبدأ «الكود هو الحقيقة»): 28 من 71 شاشةً في الوحدات الخمس المُهاجَرة **لا تُحَلّ بالمسار** — أغلبها نقاط AJAX لا تمرّ بالمُنفِّذ أصلًا، لكن بينها شاشاتٌ حقيقية مسجَّلة **بكودٍ قصير** (مثل `equipments.php`). إنفاذٌ مباشر على بادئات الوحدات المُهاجَرة كان **سيكسرها** — خرقًا لقاعدة صفر الكسر. لذا فُعِّل النمط المرحلي المعتمد في المنظومة (نمط CSRF وحارس الأفعال وبوابة العزل ذاته): **الإنفاذ فارغٌ افتراضًا + المراقبة مفعَّلة على البادئات الخمس** تجرد تلك الشاشات في `logs/security.log` تمهيدًا لتسجيلها ثم قلبِ الإنفاذ، **وآلية الـ403 نفسها مُبرهَنة اليوم** على بادئةٍ رميّة:

### مخرَج `tests/proof_failclosed.php` حرفيًّا (تشغيل 2026-07-14 — دخولٌ فعليّ وخادمٌ حيّ)

```
دخول (u7 «اروينا»): AUTH ✓ · الجلسة متماسكة: ✓

(أ) مراقبة  Finance/zz_fc_monitor_probe.php → HTTP 200  (المتوقع 200، شفّافٌ مرصود)
(ب) إنفاذ   zzfc/zz_fc_enforce_probe.php  → HTTP 403  (المتوقع 403) · جسمٌ JSON unregistered_screen ✓
(ج) فارغ    zzfc/zz_fc_enforce_probe.php  → HTTP 200  (المتوقع 200، الافتراض الإنتاجيّ آمن)

── سطور logs/security.log الجديدة ──
  [2026-07-14 01:43:53] [UNREGISTERED_SCREEN_WOULD_DENY] IP: ::1 | User: اروينا (7) | Event: UNREGISTERED_SCREEN_WOULD_DENY | Details: path=/ems/finance/zz_fc_monitor_probe.php prefix=/finance/ (monitor; deadline=2026-09-30) | UA: Mozilla/5.0 EMS-FailClosedProof
  [2026-07-14 01:43:54] [UNREGISTERED_SCREEN_DENY] IP: ::1 | User: اروينا (7) | Event: UNREGISTERED_SCREEN_DENY | Details: path=/ems/zzfc/zz_fc_enforce_probe.php prefix=/zzfc/ role=4 | UA: Mozilla/5.0 EMS-FailClosedProof

  (أ) مراقبة 200 + WOULD_DENY مسجَّل   ✓
  (ب) إنفاذ 403 + DENY مسجَّل + JSON    ✓
  (ج) فارغ 200 (صفر تغيير سلوك)         ✓

PASS: الصمّام يحجب غير المسجَّل تحت الإنفاذ (403)، يرصد تحت المراقبة (شفّاف)، وآمنٌ فارغًا (200)
```

«لقطة 403 لمسارٍ وهمي»: السطر (ب) — مسارٌ وهمي `zzfc/zz_fc_enforce_probe.php` أُجيب بـ**HTTP 403** وجسم `{"error":"unregistered_screen",…}` وسُجِّل سطر `UNREGISTERED_SCREEN_DENY` الحرفي أعلاه. قُدِّم برهانًا نصّيًّا ذاتيَّ التشغيل بدل لقطة الشاشة الثابتة — قابلٌ للتكرار عند أي مراجعة بـ`php tests/proof_failclosed.php`.

دخانُ عدم الكسر: 5 شاشاتٍ حقيقية (منها `equipments.php` المسجَّلة بكودٍ قصير) طُلبت تحت المراقبة الفعلية = **200 كلها بلا fatal**، مع أسطر جردٍ صحيحة.

**معيار القبول** (شاشة غير مسجَّلة تحت بادئةٍ مُهاجَرة تُحجَب 403 وتُسجَّل، والنواة القديمة شفافة بمهلةٍ معلنة): ✓ الآلية مستوفاة ومُبرهَنة؛ قلبُ الإنفاذ على البادئات الخمس رهنُ اكتمال جرد المراقبة (خطوة تسجيل شاشاتٍ لا خطوة كود).

## §4 — البند 4: سور المُرحِّل ضد جدولٍ جديدٍ بلا company_id

### التنفيذ

في `database/migrate.php` حول تنفيذ كل ملف ترحيل: لقطةُ جداولٍ قبل، فحصٌ بعد — أيُّ جدول أساسٍ جديدٍ **بلا `company_id`** وغير مصنَّفٍ في عقد البوابة تصنيفًا غير مستأجَر (`T_GLOBAL`/`T_CHILD`/`T_CATALOG`/`T_RESTRICTED`) → **يُسقَط فورًا** (تراجُع إنشائه)، يُسجَّل الملف فاشلًا، ويتوقّف التطبيق. غير المسجَّل في العقد إطلاقًا = **غير معفيّ** (fail-closed).

### مخرجا ترحيلَي البرهان حرفيًّا (تشغيل 2026-07-14)

**(أ) الأعمى — محجوب:**

```
تطبيق 2026_07_14_zz_bad_probe.sql ...
  ✘ فشل: MIGRATION BLOCKED: جدول(جداول) جديدة بلا company_id وغير مصنَّفة عالميًّا/ابنًا في العقد: zz_bad_probe — أُسقطت. أضف company_id (+backfill+فهرس) أو سجِّل التصنيف في TenantRegistry أولًا.
[migrate] توقّف عند أول فشل. عالج السبب ثم أعد `up` (الملفات idempotent).

هل الجدول الأعمى موجود بعد الصدّ؟
لا — أُسقط تلقائيًّا ✓
```

**(ب) السليم (بـ company_id) — نافذ:**

```
تطبيق 2026_07_14_zz_ok_probe.sql ...
  ✔ نجح (35ms)
```

**الحالة الختامية بعد تنظيف المسبارَين:** `applied=18 baseline=32 pending=0 failed=0 modified=0 missing=0` · جداول zz متبقية: 0.

**معيار القبول** (ترحيلٌ بجدولٍ أعمى يُصَدّ ويُسقَط، وترحيلٌ سليم يمرّ): ✓ مستوفى.

## خاتمة — حالة السلامة الكلّية بعد البنود الأربعة

- **الدفتر المقدّس**: `fin_financial_events` = **10 أحداث** قبل وبعد كل برهان (مُقاسٌ في مخرَج كل سكربت) — MAX(id)=55، مستهلك المالية cursor=141 لم يُمَسّ.
- **كود الناقل** (`EventPublisher` / `EventDispatcher` / `timesheet_event_hook` / `cron_events`): **صفر تعديل** — البراهين مرَّنته ولم تلمسه.
- **صفر كسر**: دخان 5 شاشات حقيقية 200 بلا fatal؛ الإنفاذان الجديدان (الصمّام والسور) fail-closed على الجديد وشفافان على القائم.
- **البراهين مؤرشفة قابلة لإعادة التشغيل**: `tests/proof_correction.php` · `tests/proof_orphan.php` · `tests/proof_failclosed.php` — كلّها ذاتية التنظيف.

باستيفاء البنود 1–4 وتثبيت شرطَي 5–6 نصًّا في v5 §35، نلتمس توقيع **«مرحلة الأساسات مكتملة 100٪»** وفق ختام طلبكم. *(ملاحظة توقيت: هجرة الصيانة المذكورة في ختام الطلب كانت قد أُنجزت فعلًا 9/9 خلف البوابة قبل وصوله، ضمن تقدّم المرحلة 3 الموثَّق في v5 §30 — خمس وحداتٍ من ستٍّ مكتملة.)*
