# العقد التقني لبوابة العزل / DAO — Tenant Gate Contract

**المرجع:** ADR-02 (EQUIP-ARC-R02 §2) · **هذا هو المخرَج ⑥** من حزمة المراجعة
**التنفيذ:** 2026-07-07 · **الكود:** `app/Core/` · **الاختبارات:** `tests/tenant_leak_test.php`
**الإلزام:** يقيّد بندَي معيار القبول المعماري §4: ① (كل استعلام عبر البوابة، لا mysqli خامًا) و② (اجتياز اختبار التسرّب قراءةً وكتابةً).

---

## 1. المبدأ والنطاق

- البوابة (`App\Core\TenantDb` عبر `ems_tenant_db()`) هي **الطريق الوحيد** لوصول الشاشات **المُهاجَرة** والوحدات **الجديدة** إلى قاعدة البيانات.
- الشاشات القديمة تبقى على mysqli الخام **حتى دور هجرتها** (R02 §3.4) — البوابة لا تغيّر سلوكها إطلاقًا (غير كاسرة بالبنية).
- المؤشر الحاكم (R02 §7): «نسبة الاستعلامات المارّة عبر البوابة = 100% **للشاشات المُهاجَرة**».

## 2. الضمانات (ما تتكفل به البوابة — لا يكتبه المطوّر أبدًا)

| الضمان | الآلية |
|---|---|
| عزل الشركة قراءةً | حقن `company_id = سياق الجلسة` آليًا في كل SELECT/COUNT |
| عزل الشركة كتابةً | فرض `company_id` على INSERT؛ تقييد UPDATE/softDelete بنطاق الشركة |
| منع تمرير الهوية | `TenantContext` يُبنى من الجلسة (`fromSession`) أو من الخادم (`forSystem`) حصريًا — لا مسار يقرأ هوية من `$_POST/$_GET`؛ تمرير `company_id` مغايرٍ في البيانات = **رفض + تسجيل «identity forgery»** |
| Fail-Closed | جدول غير مسجَّل / سياق بلا شركة / معرّف غير سليم / تلاعب بـ company_id في whereRaw ⇒ `TenantGateException` + حدث `tenant_gate_violation` في security.log |
| حقن SQL | prepared statements دائمًا؛ كل المعرّفات ضد `^[A-Za-z0-9_]+$` والسجل |
| أرشفة لا حذف (§4 ⑧) | لا يوجد DELETE في الواجهة أصلًا — `softDelete()` فقط، ويُرفض على جدولٍ بلا أعمدة حذفٍ ناعم؛ القراءة تستبعد المحذوف افتراضيًا (`includeDeleted` صريح) |
| التجاوز المرئي | القراءة العابرة للشركات عبر `forAllTenants($reason)` فقط: مدير أعلى حصرًا + تسجيل كل استدعاء (`tenant_gate_cross_tenant`) بموقع الاستدعاء والسبب |

## 3. سجل الجداول (`TenantRegistry`) — أربع فئات

| الفئة | العدد | السلوك |
|---|---|---|
| `T_TENANT` | 121 | حقن العزل قراءةً وكتابةً (+ علم `soft` للحذف الناعم) |
| `T_CHILD` | 3 | بلا company_id — يُعزل عبر أبيه (`EXISTS` على الأب)؛ إدراج ابنٍ يتحقق أن الأب مملوك للمستأجر |
| `T_GLOBAL` | 7 | مراجع نظام (roles، modules...): قراءة متاحة، كتابة للمدير الأعلى فقط |
| `T_RESTRICTED` | 10 | منصة/محرّكات لم تُهاجَر (admin_*، approval_*، schema_migrations...): **مرفوضة كليًا** حتى يُعرَّف عقدها مع هجرة وحدتها |

**قاعدة الجداول الجديدة:** أي جدولٍ يُنشأ بترحيلٍ يُسجَّل هنا في نفس الـ commit مصنَّفًا بوعي (مع `company_id` وأعمدة الحذف الناعم للمستأجَر — معيار §4). جدولٌ غير مسجَّل غير قابلٍ للاستخدام عبر البوابة أصلًا.

## 4. الواجهة (API)

```php
$gate = ems_tenant_db();   // هوية الجلسة الحالية — من config.php

$rows = $gate->select('mnt_breakdown', [
    'columns' => ['id', 'title', 'status'],
    'where'   => ['status' => 'open'],                 // تساوٍ مرتبط بمعاملات
    'whereRaw'=> 'created_at >= ?', 'params' => [$d],  // جزء حرٌّ يكتبه المطوّر (القيم عبر ? حصريًا)
    'orderBy' => 'id DESC', 'limit' => 50, 'offset' => 0,
]);
$row = $gate->selectOne('clients', ['where' => ['id' => $id]]);   // null إن لم يكن لمستأجرك
$n   = $gate->count('contracts', ['where' => ['status' => 1]]);
$id  = $gate->insert('mnt_breakdown', $data);          // company_id يُحقن — لا تمرّره
$aff = $gate->update('mnt_breakdown', $set, ['id' => $id]);
$aff = $gate->softDelete('clients', $id);              // ناعم حصريًا
$all = $gate->forAllTenants('لوحة إشراف المنصة');       // مدير أعلى + مسجَّل
```

**محظورات على المطوّر في الشاشات المُهاجَرة** (يكشفها grep في المراجعة):
- أي `mysqli_query/prepare` مباشر — البند ① من §4.
- ذكر `company_id` في أي `where/whereRaw/data` — العزل مسؤولية البوابة وحدها (المخالفة تُرفض runtime أيضًا).
- التقاط `TenantGateException` لإسكاته — الاستثناء يعني خللًا بنيويًا يُصلَّح لا يُبتلَع.

Setup/Teardown ذاتيان (شركتا اختبارٍ مؤقتتان).
- **قاعدة الاعتماد (§4 بند ②):** كل شاشةٍ تُهاجَر تُضاف إلى `$MIGRATED_SCREENS` في ملف الاختبار، ولا تُعتمد إلا والحزمة كلها خضراء — «اختبارات التسرّب خضراء على كل شاشةٍ مُهاجَرة» هو معيار خروج المرحلة 1 حرفيًا.

## 6. حدود النسخة الأولى (مقصودة وموثقة)

- **لا JOIN مبنيًا بعد** — شاشات القوائم البسيطة (نطاق المرحلة 2) لا تحتاجه؛ يُضاف عند أول هجرةٍ تتطلبه **بتحديث هذا العقد واختباراتٍ له** (كل جدولٍ مستأجَرٍ في الـ JOIN يُعزل).
- سياق `forSystem` لواجهة `api/` المحمولة: الهوية من token خادمي — على مستدعيه ألا يمرر قيمة من العميل أبدًا (نفس عقد المصدر الموثوق).
- الجداول المقيَّدة العشرة تنتقل من `T_RESTRICTED` إلى فئتها الصحيحة كلٌّ مع هجرة وحدته (محرّك الموافقات مع ADR-08...).

## 7. وضع المراقبة log-only (K1 · أُضيف 2026-07-08 — بند ADR-02 الصريح)

**الدلالة (نمط `EMS_CSRF_ENFORCE`/`CSRF_ENFORCE_PATHS` حرفيًا):**

| التهيئة في `.env` | السلوك |
|---|---|
| غياب `EMS_TENANT_GATE` أو `=enforce` | **fail-closed صافٍ** (الافتراض الآمن — سلوك العقد أعلاه بلا تغيير) |
| `EMS_TENANT_GATE=monitor` | حالات سياق العزل الثلاث فقط (جدول غير مسجَّل · جدول مقيَّد · لا شركة في السياق) **تُسجَّل `tenant_gate_would_deny` ثم تُمرَّر بسلوك ما قبل الهجرة** — قراءةً وإدراجًا حصرًا |
| مسار في `TENANT_ENFORCE_PATHS` | **fail-closed حتى في monitor** — هذا هو «التفعيل شاشةً شاشة» في تسلسل ADR-02 |

**ما لا يعبر أبدًا (يُرفض في الوضعين):** تزوير الهوية (تمرير `company_id`) · `update`/`softDelete` عبر أي عبور مراقبة (strict) · `update` بلا شرط · الحذف الصلب · كتابة مرجعٍ عام · ابنٌ لأبٍ غير مملوك · `company_id` في whereRaw · معرّفات/orderBy فاسدة · أخطاء prepare/execute. **والمسار السوي المعزول مطابقٌ بايتًا ببايت في الوضعين** — monitor لا يلمسه.

**التغطية الاختبارية:** القسم 6ب في `tests/tenant_leak_test.php` (8 تأكيدات m1–m7) — الحزمة كاملة 35/35.

## 8. قناة replaceChildren (أُضيفت 2026-07-08 — قرار K9-M1/جـ)

**قناة استثنائية معرَّفة بدقة — ليست ثغرة في «لا حذف صلبًا»**: نمط «الاستبدال الكامل» التقني (تحرير أبٍ يعيد كتابة كل سطور تفاصيله) ليس حذفَ سجلِّ أعمالٍ يُؤرشَف، بل إعادة كتابة نسخة عمل. سجلات الأعمال تبقى على softDelete حصرًا.

`replaceChildren($parentTable, $parentId, $childTable, $parentCol, array $rows, $note)`
- **نطاق مزدوج إلزامي**: ملكية الأب لشركة السياق تُتحقق صراحةً (**و**) حذف الأبناء مشروط بالأب والشركة معًا — لا يكفي أحدهما.
- **ذرّية**: الحذف والإدراج في معاملة واحدة — أي فشلٍ = rollback كامل (لا تضيع السطور القديمة دون الجديدة). تدير معاملتها — لا تُستدعى داخل معاملة مفتوحة.
- **أثر إلزامي**: كل استدعاء يُسجَّل `tenant_gate_replace_children` (تحذف بيانات).
- **قيد استخدام**: أي شاشة تستعملها تُبرّر في هجرتها أنها نمط أب-أبناء فعلًا (مثال معتمد: سطور أوامر/طلبات/عهد المشتريات وحركات المخزون المعاد احتسابها).
- **التغطية**: القسم 6جـ في حزمة التسرّب (c1–c5: استبدال مشروع بذرّية وعدّ دقيق · أب غير مملوك يُرفض · شركة أخرى لا تُمسّ · فساد وسط الدفعة = لا شيء · الأثر مسجَّل).

## 9. قناة runInTransaction (أُضيفت 2026-07-08 — قرار K9-M1/2)

**للعمليات النطاقية المترابطة متعددة الجداول** (مثال معتمد: صرف المخزون — سطور ← حركات ← عهدة بترابط line_id الوليد): معاملة واحدة تجري داخلها عمليات بوابة متعددة بذرّية مشتركة.

`runInTransaction(callable $work, $note)` حيث `$work = function(TenantDb $gate): mixed`
- **الحراسة لا تتعلق أبدًا**: كل عملية داخل الـcallable هي دوال البوابة نفسها بحُرّاسها كاملةً — فتح المعاملة لا يمنح إعفاءً؛ أي رفضٍ داخلي (تزوير/ملكية/سجل) = rollback الكل.
- **الذرّية المشتركة**: أي استثناء في أي نقطة = تراجع كل ما سبق. `insert()` يعيد المعرّف الوليد فورًا — مرئي للعمليات التالية (الترابط).
- **تبنّي القنوات الداخلية**: `replaceChildren` داخلها تتبنّى معاملة المدير (لا begin متداخل = لا commit ضمني) — مُثبَت اختبارًا (t4).
- **لا تداخل**: استدعاء داخل معاملة مُدارة قائمة يُرفض. كل معاملة تُسجَّل (`tenant_gate_transaction`) بنتيجتها.
- **التغطية**: القسم 6د (t1–t5): نجاح+ترابط، فشل وسطي=تراجع الكل، تزوير داخلي=رفض+تراجع، تبنّي replaceChildren، رفض التداخل.

## 10. قناة scopedQuery (أُضيفت 2026-07-08 — قرار K9-D/ب)

**للقراءات المركّبة/التجميعية** (GROUP BY/JOINs — مثل دفاتر المخزون) التي تتجاوز CRUD والترطيب الثنائي: المطوّر يعلن الجداول ويضع `{TENANT_SCOPE}`، **والبوابة تبني شروط العزل بنفسها**.

`scopedQuery(array('scope'=>[alias=>table,...], 'enrich'=>[...]), $sqlWithToken, $params)`
- **ضمانة «العزل النافذ لا النصي»** (تدقيق المستخدم): وجود الرمز لا يكفي — يُتحقق بنيويًا (مسح بعمق الأقواس بعد تجريد النصوص المقتبسة) أنه: مرة واحدة، على العمق 0، بعد `WHERE` العلوية الوحيدة، وقبل أي `GROUP BY/HAVING/ORDER BY/LIMIT` علوي — أي في موضع ترشيح مصادر الصفوف قبل التجميع. `UNION` مرفوض كليًا. **والبرهان التجريبي المكمِّل إلزامي**: اختبار تسرّب §7 لكل شاشة مستهلكة.
- `scope` = جداول مصادر الصفوف: تُحقن `alias.company_id = ?` لكلٍّ. `enrich` = إثراء بمفتاح من صفوف معزولة: **LEFT JOIN حصرًا** (يُتحقق)، بلا شرط WHERE (يقلب LEFT إلى INNER) — **قيد النسخة**: عزله عبر مفاتيح الصفوف المعزولة واختبار الشاشة، لا شرطًا محقونًا.
- أي جدول مستأجر مسجَّل يظهر مصدرًا دون إعلان = رفض · `company_id` يدوي = رفض · SELECT فقط · قناة كود جديد (لا عبور مراقبة).
- **التغطية**: القسم 6هـ (e1–e7): تجميع GROUP BY حقيقي عبر شركتين معزول + الرفض البنيوي الستّي.
